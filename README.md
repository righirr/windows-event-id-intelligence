# Event ID Field Guide

A searchable field guide to Windows Event IDs. **Its core scope is Windows Auditing (Security) Logs and Sysmon Logs** — together the two richest sources of security telemetry Windows produces — with supporting coverage of the System, Application and PowerShell-Operational logs, since real investigations constantly need to cross-reference all of them. The app adds charts, a word cloud, a sortable table, an attack-technique lookup table, and — for a growing subset of events — a genuine real-world log example alongside the synthesized one.

- **Live app (Artifact):** https://claude.ai/artifact/6byjkR49WGEAGu7kQATkDm
- **Current version:** 2.0 — see [RELEASE_NOTES.md](RELEASE_NOTES.md)

## Real-world log examples (v1.4)

Every specimen ships with a **synthesized** example log, built by filling Microsoft's own message field templates with representative sample data (`j.doe`, `CONTOSO`, sample SIDs, etc.) — useful for learning the shape of an event, but not a real capture.

As of v1.4, **8 events** also carry a second, **genuine** log line lifted verbatim (reformatted only for legibility) from Fortinet's own FortiSIEM documentation of what its Windows Agent / Windows Host Collector actually captures in the field:

| Log | Event ID | What it shows |
|---|---:|---|
| Security | 4703 | Real "token right adjusted" event from a live Windows 10 host |
| Security | 4798 | Real "local group membership enumerated" event — captured from a **French-locale** Windows host, a nice demonstration that the Event ID and field structure stay constant across languages even though Windows localizes the message text |
| System | 7036 | Real service-state-change event (Microsoft Store Install Service stopping) |
| Application | 16384 | Real Software Protection Platform (licensing) event |
| PowerShell | 600 | Real "WSMan provider started" event |
| PowerShell | 403 | Real "engine state changed to Stopped" event |
| Sysmon | 1 | Real process-creation event, captured on a FortiSIEM collector host itself |
| Sysmon | 13 | Real registry-value-set event |

Researching that Fortinet page also surfaced **two Event IDs that weren't in the catalogue yet** — PowerShell 600 (Provider Lifecycle) and 403 (Engine Lifecycle — Stopped) — plus Application 16384 (Security-SPP), all now added as full entries. In the app, look for the 🧾 "verified capture" badge, or use the "🧾 Real examples only" filter chip above the table.

## Why this isn't "every Windows Event ID"

A fair question was raised (back when this catalogue stood at 436): doesn't Windows have *way* more event IDs than that? Running

```powershell
Get-WinEvent -ListProvider * -ErrorAction SilentlyContinue | Select-Object Name -ExpandProperty Events | Measure-Object
```

on a real machine returns a number in the thousands — sometimes tens of thousands. That command and this app are measuring two fundamentally different things:

- `Get-WinEvent -ListProvider *` enumerates **every ETW event provider registered on that specific machine** — typically 800–1,500+ of them, including every driver, OEM utility, browser, antivirus, and piece of installed software — and sums every event *definition* each one declares in its manifest, whether or not it has ever actually fired.
- **Event IDs are not globally unique.** They're only unique within a given *(Provider, Log)* pair. Event ID 1000 from `Microsoft-Windows-Security-Auditing` and Event ID 1000 from some unrelated third-party driver are two completely different events that happen to share a number. Summing across all providers answers "how many (provider, ID) pairs exist on this one machine," not "how many Windows Event IDs exist."
- That count is also **machine-specific and non-deterministic** — a different PC, with different drivers and software installed, returns a different number. There is no fixed, universal total to catalogue.
- Many declared event definitions are **reserved or never fire** in practice; the manifest can define far more than what shows up in a real log.

This guide is deliberately scoped to the **documented, security-relevant, cross-machine-stable** event IDs an analyst or student would actually want to search — the full official Security Auditing catalogue, plus the handful of System/Application/PowerShell/Sysmon events that show up constantly in real-world threat hunting and incident response — rather than an exhaustive, machine-dependent dump that would mostly be undocumented noise from random drivers and installed software.

## Possible future expansion

If broader coverage is wanted, the next logical additions are other well-known "Applications and Services Logs" channels that are commonly monitored for security purposes but sit outside the base Security/System/Application logs, e.g.:

- Task Scheduler Operational
- Windows Defender Operational
- Group Policy Operational
- Terminal Services / RDP
- Windows Firewall Operational
- Kerberos KDC
- Certificate Services
- DNS Server / DNS Client

None of these are in the current 462; they were intentionally left out to keep the initial scope focused on the base three logs plus PowerShell and Sysmon.

## Running it yourself (Docker)

The whole app is one self-contained `index.html` (data, styles and JS are embedded into it by the project's own build step), so hosting it is just serving a static file. The included `Dockerfile` and `docker-compose.yml` do that with a small nginx image:

```bash
# from this folder
HOST_IP=192.168.3.100 HOST_PORT=8080 docker compose up -d
```

Then open `http://192.168.3.100:8080/` from any device on that network. `HOST_IP`/`HOST_PORT` default to `0.0.0.0`/`8080` if omitted (see `.env.example`); enter the same IP and port into the app's own **⚙ Settings** panel and it'll show that Access URL on the main page for anyone else using that browser.

Without Docker, a quick one-liner also works for local testing — the Settings panel generates this for you too:

```bash
python3 -m http.server 8080 --bind 192.168.3.100
```
